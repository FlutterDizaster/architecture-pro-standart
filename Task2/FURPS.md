# Задание 2. Требования в формате FURPS+

Собрал требования по депозитам (MVP) и по кредитам. Буквами АЗ в комментарии отметил архитектурно значимые требования. Большая часть из них лежит в разделе +R, но несколько функциональных тоже влияют на архитектуру, поэтому отметил и их. Требования, которых не было в описании, помечены как «доп.», рядом обоснование.

| Код | Требования | Комментарий |
|-----|------------|-------------|
| F | Функциональные (Functionality) | |
| | Депозиты, MVP | |
| F1 | На сайте новый клиент видит список депозитов и накопительных счетов с актуальными ставками | АЗ: сайту нужен источник ставок, сейчас их нет нигде, кроме Excel |
| F2 | На сайте клиент оставляет заявку на депозит: телефон и Ф. И. О. | |
| F3 | Заявка с сайта попадает в систему кол-центра, менеджер кол-центра видит её, звонит клиенту и может предложить особые условия | АЗ: новая интеграция сайта с системой кол-центра |
| F4 | После звонка новый клиент приходит в отделение для идентификации, депозит открывается там | Банк не может принять нового клиента без личной проверки документов |
| F5 | В интернет-банке клиент видит список депозитов и накопительных счетов с актуальными ставками и персональные ставки для себя | АЗ: персональная ставка считается из данных депозитного и кредитного бэк-офисов |
| F6 | В интернет-банке клиент выбирает депозит, указывает счёт списания и сумму и подаёт заявку | |
| F7 | Подача заявки в интернет-банке подтверждается СМС-кодом | АЗ: СМС есть в ядре интернет-банка, но его доработка у подрядчика, поэтому нужна отправка кодов в обход ядра |
| F8 | Ставки по депозитам ведутся в одной системе, а не в XLS-файлах. С ними работают бэк-офис депозитов и бэк-офис кредитов | АЗ: предлагают сделать в АБС вместе с процессом согласования ставки по заявке |
| F9 | В MVP заявку из интернет-банка обрабатывает менеджер бэк-офиса: подтверждает ставку и условия депозита в АБС | |
| F10 | Клиент получает СМС после подтверждения ставки и после открытия депозита | |
| F11 | Сотрудники депозитов не видят кредитные данные клиента, а сотрудники кредитов не видят депозитные | Требование безопасности из текущего процесса, его нужно сохранить в новом справочнике ставок |
| F12 | Клиент видит в интернет-банке статус своей заявки на депозит | Доп. Без статуса клиенты старшего возраста будут звонить в кол-центр и спрашивать, что с заявкой |
| | Кредиты | |
| F13 | На сайте клиент видит предложение кредита со ставкой. Полные условия хранятся в Кредитном конвейере | АЗ: сайт получает условия из Кредитного конвейера |
| F14 | На сайте клиент оставляет заявку на кредит: телефон и Ф. И. О. Если он заполнит паспортные данные, то сразу получает предварительное решение | АЗ: для нового клиента скоринг идёт только по общим данным БКИ |
| F15 | После заявки с сайта клиент получает СМС, что нужно прийти в отделение за кредитом и для идентификации | |
| F16 | В отделении менеджер продолжает работу с той же заявкой, если клиент уже подавал её на сайте. Для нового клиента создаётся новая заявка | АЗ: заявка с сайта должна быть доступна из отделения, нужен поиск по клиенту |
| F17 | В интернет-банке клиент видит список кредитов с актуальными условиями и предодобренное предложение, если по нему уже был скоринг | |
| F18 | Клиент подаёт заявку на кредит в интернет-банке: счёт зачисления и данные заявки, подтверждение СМС-кодом | |
| F19 | По заявке на предодобренный кредит скоринг повторяется по упрощённой процедуре, если ситуация клиента изменилась | |
| F20 | Клиент получает СМС при каждом изменении статуса заявки на кредит | |
| U | Удобство использования (Usability) | |
| U1 | Интерфейсы сайта и интернет-банка сделаны по системе дизайна банка: привычные цвета, брендированные элементы | |
| U2 | Подача заявки на депозит в интернет-банке занимает не больше трёх шагов: выбор депозита, сумма и счёт, СМС-код | Доп. Основные клиенты банка люди старшего возраста, длинный сценарий они бросят |
| U3 | Тексты СМС и экранов короткие и понятные, без банковских терминов | Доп. Та же причина, плюс меньше звонков в кол-центр |
| R | Надёжность (Reliability) | |
| R1 | Сервисы онлайн-каналов работают 24/7 с доступностью 99,9% | АЗ |
| R2 | При сбое основного ЦОД сервисы интернет-банка продолжают работать в резервном ЦОД и держат требуемую нагрузку | АЗ: сейчас резервный ЦОД есть, но включается вручную |
| R3 | Онлайн-заявки не должны влиять на работоспособность АБС | АЗ: БД АБС уже перегружена |
| R4 | Заявка клиента не теряется, если АБС или Кредитный конвейер временно недоступны: она доставляется после восстановления | Доп. При асинхронной передаче заявок это обязательное свойство, иначе клиент подаст заявку и ничего не получит |
| R5 | Кредитный конвейер и система скоринга работают 24/7 | Уже выполнено, учитываем как свойство систем |
| P | Производительность (Performance) | |
| P1 | Отклик по операциям в интернет-банке измеряется миллисекундами, справочные данные (ставки, условия) отдаются быстрее секунды | АЗ: сейчас справочники при платежах грузятся больше секунды |
| P2 | Сервисы интернет-банка масштабируются горизонтально, запросы распределяются между серверами, приложениями и ЦОД | АЗ |
| P3 | Заявки на кредит по предодобренным предложениям обрабатываются в тот же рабочий день | АЗ: суточный обмен АБС и Кредитного конвейера ускорить нельзя, нужен другой путь доставки заявки |
| P4 | Решение по кредитной заявке из онлайн-каналов клиент получает в течение одного дня, если данных достаточно | Цель бизнеса на год |
| P5 | Система скоринга не получает дополнительной нагрузки от предрасчётов скоринга | АЗ: предодобренные предложения строим на результатах уже проведённых скорингов |
| S | Поддерживаемость (Supportability) | |
| S1 | Для новых сервисов и интеграций есть документация, чтобы систему можно было расширять | АЗ: контракты API и событий описываем в OpenAPI и AsyncAPI |
| S2 | Ставки и условия депозитов меняет бизнес без релиза | Доп. Ставки меняются каждый день |
| S3 | По каждой заявке есть сквозной идентификатор и журнал статусов во всех системах | Доп. Заявка проходит через 3–4 системы, без сквозного идентификатора разбор обращений клиента займёт часы |
| +R | Ограничения (Restrictions) | |
| +R1 | Новые компоненты делаем на технологиях, которые уже есть в банке: .NET, Java, Python, PHP, React, БД MS SQL, Oracle, PostgreSQL | АЗ |
| +R2 | Новые технологии допустимы, если они совместимы с текущими платформами и в банке есть хотя бы базовая экспертиза | АЗ |
| +R3 | Для очередей сообщений используем Kafka | АЗ: текущая платформа интернет-банка с Kafka несовместима, нужен промежуточный сервис |
| +R4 | Функционал депозитов в интернет-банке выносим в отдельные сервисы, монолит не расширяем | АЗ: обновление ядра монолита зависит от подрядчика |
| +R5 | Ядро интернет-банка (СМС) не дорабатываем, бизнес-функции пишет команда банка | АЗ |
| +R6 | В новых процессах (депозиты, кредиты) интернет-банк не работает с АБС напрямую: ни через БД, ни через API АБС | АЗ: защищаем перегруженную БД АБС. Текущая интеграция платежей и счетов через БД пока остаётся |
| +R7 | АБС масштабируется только вертикально | АЗ: свойство БД АБС, нагрузку на неё снимаем кешем и асинхронным обменом |
| +R8 | Данные между клиентом и сайтом, клиентом и интернет-банком передаются только по защищённому каналу (TLS) | АЗ: передаются персональные данные |
| +R9 | Систему кол-центра дорабатываем своими Java-специалистами из команды АБС через механизмы расширения платформы | АЗ |
| +R10 | Обмен АБС и Кредитного конвейера раз в сутки через БД сохраняется, ускорить его нельзя | АЗ |
| +R11 | Новый клиент с сайта скорится только по общим данным БКИ | АЗ |
